# Выпуск Desktop App

Работай в корне репозитория. Порядок выпуска и действия при сбое описаны в [docs/release.md](../../../docs/release.md), workflow `release` — в [docs/ci.md](../../../docs/ci.md#release), форматы — в [docs/packaging.md](../../../docs/packaging.md). Скилл задаёт границы поручения и что проверить на каждом шаге; механику выполняют задачи `release:plan`, `release:verify`, `release:promote`, `git` и `gh`. Если скилл расходится с документами или `Taskfile.yml`, верны они.

## Объём поручения

- Просьба спланировать выпуск или написать описание разрешает только чтение: `wails3 task release:plan`, разбор коммитов, ревизию документации, предложение версии и черновик описания.
- Commit, push, тег, перезапуск workflow, правка черновика и публикация — только по явному поручению. Поручение на один шаг не распространяется на следующие. Поручение «выпусти версию X.Y.Z» разрешает все шаги до публикации включительно; повторно не спрашивай.
- Прямой запрет на коммиты, теги или публикацию важнее.
- Опубликованный выпуск и его тег не удаляются и не переносятся: ошибку исправляет следующая patch-версия.

## Состав выпуска

Список форматов — переменная `RELEASE_FORMATS` в `Taskfile.yml`; имена файлов задаёт `updater.Naming` из go-desktop-kit. Полный состав для версии печатает:

```bash
go tool relkit names -app desktop-app -version 1.2.3
```

Для шаблона это семь пакетов (deb, rpm, Arch, AppImage, dmg, установщик NSIS, переносимый exe) и три файла сумм (`SHA256SUMS-linux.txt`, `SHA256SUMS-macos.txt`, `SHA256SUMS-windows.txt`). Все пакеты собирает CI по тегу; локально собирать их для выпуска не нужно. Пакеты не подписаны — в описании выпуска не обещай подписи и отсутствия предупреждений SmartScreen и Gatekeeper.

## Порядок

1. **Предусловия.** `wails3 task release:plan` — дальше только при «Готово к выпуску: да». Красный `check` не обходи: назови упавшую ОС и разбери падение по `app-ci`. Если последний коммит был только с документами и `check` на HEAD не запускался — `gh workflow run check` (запуск workflow — по поручению) и дождись. Локально один раз `wails3 task check`.
2. **Ревизия документации.** По списку коммитов из `release:plan` сверь документы затронутых областей ([карта кода](../../../docs/code-map.md)) с кодом по существу; `README.md` и `README.en.md` совпадают по смыслу; `wails3 task check:docs` зелёный. Документ можно отдать субагенту без контекста разговора: документ, список изменённых файлов, правило сообщать расхождения с цитатой и местом в коде, ничего не меняя. Исправления — отдельным коммитом (по поручению), затем снова шаг 1. В итоге назови проверенные документы и расхождения; «расхождений нет» — тоже результат.
3. **Версия и описание.** Semver по существу изменений, а не по сообщениям коммитов: patch — исправления, minor — возможности, major — несовместимые изменения настроек или поведения. Формат `X.Y.Z` без суффиксов. Описание — по-русски, в scratchpad: что изменилось для пользователя, что сделать при обновлении, известные ограничения. Внутреннюю историю разработки и пути с машины разработчика не переноси.
4. **Тег.** Аннотированный тег на проверенный HEAD и его push — команды в [docs/release.md](../../../docs/release.md#порядок). После push `wails3 task version` печатает новую версию. Тег после push не переносится.
5. **Ожидание CI.** `gh run list --workflow release --limit 1`, затем `gh run watch <id>` в фоне. При падении назови ОС и шаг; что делать — таблица «Если что-то пошло не так» в [docs/release.md](../../../docs/release.md#если-что-то-пошло-не-так). Перезапуск — по поручению.
6. **Сверка.** `wails3 task release:verify`: все файлы состава на месте и загружены, `digest` совпадает с файлами сумм, лишних нет. Расхождение — не публиковать и разбираться. Описание выпуска вносится в черновик (`gh release edit v1.2.3 --notes-file <файл>`) по поручению.
7. **Проверка пакета.** Если владелец поручил или проверяет сам: пакет своей ОС из черновика ставится, окно открывается, на странице настроек новая версия и свой формат (`app-build`).
8. **Публикация.** Только по поручению выпустить эту версию: `wails3 task release:promote` — сверяет, публикует как `latest`, сверяет ещё раз. Ссылку давай после того, как `gh release view v1.2.3 --json isDraft` показал `false`.

При сбое сначала выясни фактическое состояние тега, черновика и вложений, затем повтори только недостающий шаг. `--clobber` не применяй, под опубликованным номером не пересобирай.

## Что сообщить

Раздельно:

- выбранную версию и почему;
- исходный SHA, чистоту дерева, итог `check` в CI и локально;
- ревизию документации;
- состояние тега, workflow `release`, черновика или опубликованного выпуска и итог `release:verify`;
- что не проверено: какие пакеты не ставились и на каких ОС.
