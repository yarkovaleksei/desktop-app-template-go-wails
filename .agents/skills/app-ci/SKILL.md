# CI Desktop App

Работай в корне репозитория. Workflows, их триггеры, фильтры путей, шаги и таблица частых падений описаны в [docs/ci.md](../../../docs/ci.md). Если скилл расходится с ним или с `.github/workflows/`, верны они.

## Объём поручения

- Чтение прогонов, журналов и артефактов не требует поручения.
- Перезапуск (`gh run rerun`), ручной запуск (`gh workflow run`), push исправления — только по поручению.
- Длинный журнал разбирай по упавшему шагу (`--log-failed`) или отдай субагенту, который читает журналы: он вернёт, что упало и почему.

## Посмотреть прогоны

```bash
gh run list --limit 5
gh run list --workflow check --branch main --limit 3
gh run view <id>
gh run view <id> --log-failed
gh run download <id>
```

Имя шага подсказывает задачу, которая упала, — соответствие в разделе [Как читать прогон](../../../docs/ci.md#как-читать-прогон). Артефакты `smoke-<ОС>` и `playwright-report` скачивает `gh run download`.

## Разобрать падение

1. **Где.** Workflow, job, ОС матрицы, шаг. Упало на одной ОС или на всех — разные причины: на одной — обычно код для одной ОС или окружение раннера, на всех — код или документы.
2. **Воспроизвести локально той же задачей.** CI запускает только `wails3 task …`: `wails3 task check`, `wails3 task check:bindings`, `wails3 task build`, `wails3 task smoke`, `wails3 task test:e2e`. Своих скриптов проверок у CI нет. Для чужой ОС без машины — `GOOS=windows go vet ./...` или `GOOS=darwin go vet ./...`.
3. **Причина.** Таблица в разделе [Как разбирать падение](../../../docs/ci.md#как-разбирать-падение). Локально зелёно — ищи, чем отличается окружение: ОС, чистый клон без кэшей, отсутствие `frontend/dist`, гонка времени в тестах.
4. **Исправление** — в коде или документах, не в обход проверки: тест не отключается и не помечается пропуском ради зелёного прогона. Песочница WebKit и AppArmor на раннере не отключаются.
5. **Случайное падение** (сеть раннера, таймаут скачивания) — `gh run rerun <id> --failed` по поручению. Повторяющееся падение случайным не считается.

## Изменить workflow

- Сначала прочитай раздел workflow в [docs/ci.md](../../../docs/ci.md); после правки обнови его в том же коммите (`app-docs`).
- Права по умолчанию — `contents: read`; запись — только job, которому она нужна. Секретов, кроме `github.token`, не добавляй без решения владельца.
- Действия закреплены по мажорной версии; новую версию действия сверяй с его выпусками на GitHub, а не по памяти.
- Шаги проверок вызывают задачи `Taskfile.yml`, а не повторяют их команды: так CI и разработчик проверяют одно и то же.
- Синтаксис — `actionlint`, если он установлен (правило для `pages.yml` — в `.github/actionlint.yaml`); нет — так и скажи, что не проверено.
- Изменённый фильтр путей проверяй мысленно на двух случаях: push только с документами (`check` не должен запускаться, `docs` должен) и push с кодом (запускаются оба).

## Что сообщить

Workflow, прогон, упавшие ОС и шаги; причину и чем она подтверждена (журнал, локальный повтор); что исправлено и какой задачей проверено локально; что осталось непроверенным до следующего прогона.
