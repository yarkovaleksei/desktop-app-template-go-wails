## Проект

Desktop App — десктоп-приложение на Go, Wails 3, React и MUI для Linux, Windows и macOS: окно с настройками, трей, автозапуск, уведомления и обновление через GitHub Releases. Назначение продукта, пользователи и границы — [spec/docs/project.md](spec/docs/project.md).

## Работа по плану

План, решения, бэклог и журнал ведутся в `spec/` по правилам [spec/AGENTS.md](spec/AGENTS.md): что читать в начале сессии, как отмечать шаги, что обновить в конце. Скилл — `app-spec`.

- Работа идёт по поручению владельца: либо «продолжай план» — тогда по следующему шагу из [spec/plan/README.md](spec/plan/README.md), либо прямое поручение — оно важнее записанного шага и выполняется, даже если в плане его нет или плана нет вовсе.
- Сам, без поручения, задачу вне плана не начинай: идею запиши в бэклог или назови владельцу.
- Поручение относится к шагу активного плана — отметь его по правилам `spec/AGENTS.md`. Разовое поручение вне плана в план не вписывается.

### Неполное поручение

Поручение редко называет всё. Если недостающее можно выбрать по документам и образцам в коде и легко переделать потом (имя поля, текст подписи, место элемента на странице, умолчание настройки), выбери разумный вариант, делай и назови выбор в отчёте. Спрашивай владельца до работы, только если выбор трудно отменить или он выходит за поручение: новая зависимость, несовместимое изменение хранимых данных (новое поле с умолчанием — совместимое), удаление, действие вне репозитория. Шаги, которые от ответа не зависят, продолжай.

## Границы поручения

- Commit, push, тег, создание и публикация выпуска, запуск workflow, установка пакетов в систему и `sudo` — только по явному поручению владельца. Поручение на один шаг не распространяется на следующие; прямой запрет важнее.
- Просьба собрать, проверить или спланировать не разрешает выпуск. Изменение рецепта сборки не разрешает пересборку всей матрицы: проверяй изменённое адресно.
- Песочница WebKit и AppArmor не отключаются ради прохождения проверки.
- Временные файлы и журналы — в scratchpad агента или `/tmp`, не в репозитории.

## Язык

- Документы, комментарии в коде, сообщения коммитов и описания PR — по-русски. Идентификаторы, имена файлов, API и устоявшиеся термины — по-английски.
- На двух языках, русском и английском, ведутся: `README.md` и его перевод `README.en.md` (меняются в одном коммите), тексты интерфейса (`frontend/src/i18n/ru.ts` и `frontend/src/i18n/en.ts`), тексты Go (`internal/texts`), сайт `www/`.
- Комментарий объясняет, зачем код и какой инвариант он держит, а не пересказывает строку.

## Устройство

Полностью — [docs/development.md](docs/development.md).

- **Граница Wails.** Wails импортируют только пакет `main` и `internal/app`. Ядро (`internal/…`) работает без окна и без фронтенда. Сервисы `internal/app` не содержат логики: вызов — в ядро, ответ — в DTO через `wire.Fill`, ошибка — в `*apperr.Error`.
- **Привязки.** `frontend/bindings` генерирует `wails3 task bindings`; каталог коммитится вместе с изменением сервисов и руками не правится. Во фронтенде привязки импортирует только `frontend/src/api/bindings.ts`, остальной код ходит в Go через интерфейс `DataSource`.
- **Ошибки.** Go отдаёт код и параметры, текст собирает интерфейс по словарю: `t("errors.<код>")`. Каждый код — в `frontend/src/i18n/error-codes.json` и в обоих словарях.
- **События.** Имена и типы — в `internal/app/events.go`, подписки с отпиской — в `frontend/src/api/events.ts`.
- **Каталоги.** Только из `appdirs` kit. `wails3 task dev` и `wails3 task smoke` работают в отдельном `DESKTOP_APP_HOME`: настоящие настройки пользователя не трогаются.
- **Имена приложения** в Go — только из `internal/appinfo`; копии вне Go сверяет `internal/archtest`.

## Код

Полностью, с тем, чем проверяется каждое правило, — [docs/code-style.md](docs/code-style.md). Скилл — `app-code-style`.

- **Go.** Ошибки оборачиваются с контекстом (`fmt.Errorf("…: %w", err)`); `context.Context` — у того, что может ждать долго (сеть, процессы, повторы); пути — через `filepath`; код одной ОС — в файлах с суффиксом ОС или build-тегом; у пакета — комментарий `// Package`, у экспортируемого — о назначении и инварианте.
- **Фронтенд.** Только yarn 4, `yarn.lock` коммитится. TypeScript строгий. Вызов Go — через `DataSource` и `call()`. Ни одной строки интерфейса в JSX: только `t("ключ")`, ключ сразу в обоих словарях.
- Новая зависимость (модуль Go, пакет npm) — только с записью решения и причины в [spec/plan/DECISIONS.md](spec/plan/DECISIONS.md).

## Интерфейс

Правила — [docs/ui.md](docs/ui.md), порядок работы над страницей — скилл `app-ui`. Сначала готовые компоненты MUI; цвета из токенов темы; каждая страница проверяется в двух темах, на двух языках и в минимальном окне 960×600. Интерфейс без Go — `wails3 task ui` (моки в браузере).

## Команды

Все задачи — в `Taskfile.yml`, запуск из корня: `wails3 task <имя>`. Нужны Go 1.26, Node 24 с `corepack enable`, `wails3` v3.0.0, на Linux — GTK 4 и WebKitGTK 6.0 (подробно — [README.md](README.md#требования-к-окружению)).

```bash
wails3 task deps            # зависимости фронтенда по yarn.lock
wails3 task dev             # окно в режиме разработки, каталоги в .task/dev-home
wails3 task ui              # интерфейс в браузере на моках, без Go
wails3 task site            # сайт www/ на локальном сервере
wails3 task check           # всё перед коммитом: зависимости, тесты, типы, линтеры, документы
wails3 task test:go         # тесты Go (адресно: go test ./internal/<пакет>)
wails3 task test:frontend   # Vitest (адресно: yarn test <файл> в frontend/)
wails3 task test:e2e        # сквозные сценарии Playwright на моках
wails3 task fmt             # отформатировать Go и фронтенд
wails3 task bindings        # перегенерировать frontend/bindings после изменения сервисов и событий
wails3 task check:bindings  # закоммиченные привязки не отстали от Go (после коммита, в CI)
wails3 task check:race      # ядро под детектором гонок
wails3 task check:docs      # ссылки, пути и задачи в документах, актуальность карты кода
wails3 task docs:map        # перегенерировать docs/code-map.md
wails3 task build           # бинарь текущей ОС в bin/
wails3 task smoke           # собранный бинарь открыл окно, фронтенд ответил
wails3 task package         # все пакеты текущей ОС в bin/
wails3 task release:plan    # только чтение: готово ли к выпуску
```

- Перед коммитом проходит `wails3 task check`. Что запустить сверх него по виду изменения — таблица в [docs/code-style.md](docs/code-style.md#перед-коммитом).
- Во время работы гоняй адресные тесты, полный `check` — перед коммитом.
- Сборки и `check` длинные: запускай их в фоне и не опрашивай без нужды.

## Документация и код

| Утверждение | Источник истины | Если код расходится |
| --- | --- | --- |
| Правила продукта и работы, контракты | документы (`AGENTS.md`, `docs/`) | исправить код; если правило выглядит устаревшим — спросить владельца |
| Наблюдаемое поведение | тесты | изменить тест только вместе с осознанным изменением поведения |
| Внутреннее устройство: пакеты, типы, алгоритмы | код и комментарии | исправить документ |

- Расхождение не разрешай молча: в итоге работы назови его и какую сторону исправил.
- Перед изменением найди область в [карте кода](docs/code-map.md); изменил поведение области — обнови её документы-владельцы в том же коммите. Скиллы — `app-code-map` и `app-docs`.
- Карта кода генерируется (`wails3 task docs:map`) и вручную не правится.
- Документы описывают назначение, правила и контракты, а не пересказывают код; история изменений живёт в Git, а не в тексте.

## Поставки и выпуск

- Сборка и проверка пакетов локально — скилл `app-build` по [docs/packaging.md](docs/packaging.md).
- Выпуск версии — скилл `app-release` по [docs/release.md](docs/release.md); только по поручению.
- Прогоны CI и правка workflow — скилл `app-ci` по [docs/ci.md](docs/ci.md).

## Git

- Основная ветка — `main`.
- Один коммит — одно логическое изменение вместе с документами, привязками и отметками плана.
- Заголовок коммита — по-русски, в повелительном наклонении («Добавить страницу журнала»); в теле — зачем и что изменилось.

## Параллельная работа

- Независимые задачи в непересекающихся файлах можно отдавать субагентам: каждому — конкретная подзадача, границы файлов, критерий приёмки и только нужный контекст, без наследования всего разговора.
- У общего изменяемого файла один владелец; зависимые шаги — последовательно.
- Основной агент интегрирует результаты и сам проверяет итоговое изменение (`wails3 task check`).
