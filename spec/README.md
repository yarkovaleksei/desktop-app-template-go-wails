# Папка spec

План проекта и всё, что нужно для его ведения: цель, этапы, бэклог, решения, журнал, описание продукта и шаблоны записей. Технические правила и устройство приложения здесь не хранятся — они в [AGENTS.md](../AGENTS.md) и [docs/](../docs/README.md).

| Что | Где |
| --- | --- |
| Правила ведения плана, бэклога, решений, журнала и сессий | [AGENTS.md](AGENTS.md) |
| Назначение продукта, пользователи, границы | [docs/project.md](docs/project.md) |
| **Единственный активный план**: цель, следующий шаг, этапы | [plan/README.md](plan/README.md) |

## Начало работы

1. Правила — [AGENTS.md](AGENTS.md): что читать в начале сессии, как отмечать шаги, что обновить в конце.
2. Активный план — [plan/README.md](plan/README.md): цель и следующий шаг. Цели нет — исполняемого шага нет, работа идёт только по прямому поручению владельца.
3. Владелец ставит цель — план составляется по разделу «Как составить план» в [AGENTS.md](AGENTS.md#как-составить-план) и показывается ему до начала работ.

Пути в тексте отсчитываются от корня репозитория, ссылки Markdown — от файла, в котором стоят. Ссылки и пути в `spec/` проверяет `wails3 task check:docs`, как и в остальных документах.

## Вынос в приватный репозиторий

`spec/` публичен вместе с кодом. Если план должен быть закрыт (обсуждения с заказчиком, планы выпусков), папка переносится в приватный репозиторий, который лежит рядом с репозиторием кода:

```text
<рабочая область>/
├── <проект>/   репозиторий кода
└── spec/       приватный репозиторий плана
```

Каталог плана называется `spec`: тогда пути вида `spec/plan/README.md` в тексте остаются верными, если отсчитывать их от рабочей области.

1. Создать приватный репозиторий и склонировать его рядом с кодом в каталог `spec`. Перенести в него содержимое `spec/` и закоммитить там. В репозитории кода удалить папку: `git rm -r spec`.
2. В перенесённых файлах ссылки, которые выходят за пределы `spec/`, получают каталог проекта: из `spec/AGENTS.md` ссылка `../AGENTS.md` становится `../<проект>/AGENTS.md`, из `spec/plan/BACKLOG.md` ссылка `../../docs/packaging.md` — `../../<проект>/docs/packaging.md`. Ссылки внутри `spec/` (из `spec/plan/` ссылка `../AGENTS.md` ведёт на `spec/AGENTS.md`) не меняются. Кандидатов найти в рабочей области: `rg -n '\]\((\.\./)+' spec`.
3. `CLAUDE.md`: импорт `@spec/AGENTS.md` заменить на `@../spec/AGENTS.md`. Claude Code при первом запуске попросит разрешить импорт из-за пределов репозитория.
4. `AGENTS.md`: в разделе «Работа по плану» сказать, что план лежит в соседнем приватном репозитории `../spec`. Каждое упоминание пути плана в репозитории кода — ссылки и пути в обратных кавычках — заменить на `../spec/…`: их находит `git grep -n 'spec/'` (`AGENTS.md`, `CLAUDE.md`, `docs/README.md`, `docs/code-style.md`, скиллы `app-spec` и `app-code-style`). Строку `spec/` убрать из раздела о структуре в `README.md` и `README.en.md`. Ссылки и пути за пределами репозитория `check:docs` не проверяет: в checkout CI соседнего репозитория нет.
5. Исключить план из проверки документов: убрать область «План проекта» из `internal/repodocs/areas.go` и перегенерировать карту кода — `wails3 task docs:map`. Markdown за пределами репозитория `check:docs` и так не обходит.
6. В правилах `spec/AGENTS.md`: сверка реальности — в обоих репозиториях (`git -C <проект> status --short`, `git -C spec status --short`, `git -C <проект> log --oneline -5`); код и план коммитятся раздельно; в журнал записывается хеш коммита кода.
7. Проверить репозиторий кода: `wails3 task check:docs` зелёный; `git grep -n 'spec/'` находит только `../spec/…` и фильтр путей `spec/**` в `.github/workflows/check.yml` и `docs/ci.md` (его можно удалить вместе с описанием).
