# Выпуск

Порядок выпуска новой версии: от проверки готовности до опубликованного выпуска на GitHub, из которого приложение получает обновления. Форматы и имена файлов — в [packaging.md](packaging.md), workflow `release` — в [ci.md](ci.md#release).

## Что нужно

- Права на запись в репозиторий GitHub (`yarkovaleksei/desktop-app-template-go-wails`, переменная `REPO` в `Taskfile.yml`).
- [GitHub CLI](https://cli.github.com/) с выполненным входом (`gh auth login`): через него `relkit` читает выпуски и запуски workflow. Токенов `relkit` не читает.
- Рабочая копия основной ветки `main`, отправленная на GitHub.

Пакеты собирает CI по тегу; локально собирать их не нужно.

## Как устроено

```text
тег vX.Y.Z ──▶ release.yml: три ОС собирают пакеты, release:collect даёт имена и суммы
                    │
                    ▼
               черновик выпуска со всеми файлами
                    │  wails3 task release:verify — состав и суммы сверены
                    ▼
               wails3 task release:promote — опубликован как latest
                    │
                    ▼
               приложение видит новую версию (черновики и пререлизы ему не видны)
```

Пока выпуск — черновик, пользователи его не получают: обновление смотрит только опубликованный `latest`. Поэтому сверка идёт до публикации.

## Порядок

1. **Состояние.** `wails3 task release:plan` — только читает: ветка и чистота дерева, совпадает ли HEAD с веткой на GitHub, прежний опубликованный выпуск и коммиты с него, последний запуск `check` на HEAD, черновики, предлагаемая версия (следующий patch; для первого выпуска — `0.1.0`). Итог — строка «Готово к выпуску: да» или «нет». Дальше — только при «да»: дерево чистое, HEAD отправлен и `check` на нём зелёный. Если последним был коммит только с документами, `check` сам не запускался: запустите его вручную (`gh workflow run check`) и дождитесь.
2. **Ревизия документации.** По списку коммитов из `release:plan`: каждое изменение поведения описано в документах своей области ([карта кода](code-map.md)); `README.md` и его перевод `README.en.md` совпадают по смыслу; `wails3 task check:docs` зелёный. Найденное исправляется отдельным коммитом, затем снова шаг 1.
3. **Версия.** Следующая версия по semver: исправления — patch (предлагает `release:plan`), новые возможности — minor, несовместимые изменения настроек или поведения — major. Формат — `X.Y.Z` без суффиксов; пререлизы не выпускаются: обновление их не видит.
4. **Тег.** Аннотированный тег на HEAD и его отправка:

   ```bash
   git tag -a v1.2.3 -m "Desktop App 1.2.3"
   git push origin v1.2.3
   ```

   После этого `wails3 task version` печатает `1.2.3`.
5. **Ожидание CI.** Workflow `release` на трёх ОС собирает пакеты и загружает их в черновик выпуска `v1.2.3`. Следить: `gh run watch` или страница Actions. Черновик появляется, только когда пакеты собрались на всех трёх ОС.
6. **Сверка.** `wails3 task release:verify` — в черновике все семь пакетов и три файла сумм, все загружены, `digest` каждого пакета равен сумме из файла сумм его ОС, лишних файлов нет. Заметки к выпуску — в черновике на GitHub: их создаёт `--generate-notes`, правятся вручную.
7. **Проверка пакетов.** Скачать пакет своей ОС из черновика и поставить его: окно открывается, на странице настроек версия `1.2.3` и свой формат. Если установлена прежняя версия из пакета, после публикации проверить обновление из приложения.
8. **Публикация.** `wails3 task release:promote` — сверяет ещё раз, публикует черновик как `latest` и сверяет опубликованный выпуск.

Команды `release:verify` и `release:promote` берут версию из тега на HEAD; на другом коммите — `wails3 task release:verify APP_VERSION=1.2.3`.

## Если что-то пошло не так

| Что | Что делать |
| --- | --- |
| `release:plan`: дерево грязное, HEAD не отправлен, `check` красный или не запускался | Закоммитить или убрать изменения, отправить, дождаться зелёного `check`; тег не ставить |
| Workflow `release` упал на сборке одной ОС | Черновика ещё нет: job `release` ждёт пакеты всех ОС. Разобрать падение ([ci.md](ci.md#как-разбирать-падение)). Если причина в окружении раннера — перезапустить упавшие jobs (`gh run rerun <id> --failed`) |
| Упал сам job `release` во время загрузки | Файлы не перезаписываются (`gh release upload` без `--clobber`), поэтому повтор на частичном черновике упадёт на первом уже загруженном файле. Удалить черновик (`gh release delete v1.2.3`, тег остаётся) и перезапустить job `release` |
| Причина в коде | Удалить черновик (`gh release delete v1.2.3`) и тег (`git push --delete origin v1.2.3`, `git tag -d v1.2.3`), исправить, выпустить следующую patch-версию. Номер версии не переиспользовать: тег мог уже попасть в чужие клоны |
| `release:verify`: файла нет или он не загружен | Дождаться конца workflow; если он закончился с ошибкой — по строкам выше |
| `release:verify`: сумма не совпала, лишний файл | Не публиковать. Удалить черновик и тег и выпустить следующую patch-версию из чистого CI |
| Пакет не ставится или окно не открывается | Не публиковать; удалить черновик и тег, исправить, следующая patch-версия |
| Ошибка найдена после публикации | Выпуск не удалять и не перезаписывать: у пользователей уже обновление. Исправить и выпустить следующую patch-версию |

## Проверить порядок всухую

До тега порядок проходится без последствий: `wails3 task release:plan` только читает GitHub и git, `wails3 task version` печатает версию сборки, а локальная сборка выпуска — `wails3 task package APP_VERSION=1.2.3` и `wails3 task release:collect APP_VERSION=1.2.3` (только файлы текущей ОС, в `dist/`).
